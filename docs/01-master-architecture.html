0.3Standing rules

Five invariants hold everywhere. A design that violates one of these is wrong regardless of how well it performs, and reviewers should reject it on that basis alone.

#InvariantEnforced by
INV-1No generated citationSection numbers, article numbers, case citations, dates and URLs are always rendered from database records. The generator emits identifiers only. L4 schema validation drops any block whose identifier does not resolve.
INV-2No answer without a passing gateThere is no code path from an abstained retrieval to a generated answer. L3 returns either a grounding context or an abstention; L4 accepts only the former.
INV-3Every answer is replayableL6 persists query, resolved filters, retrieved provision IDs with scores, gate decision, prompt hash, model version and verifier result for every response.
INV-4Provisions are the citable unitNothing outside L2 may reference a chunk identifier. Re-chunking must never invalidate a stored citation, bookmark or generated document.
INV-5Law is answered as at a dateEvery retrieval carries as_of, defaulting to today. No query path may read provision_version without a validity filter.

2.2Primary scenario — UC-03, expanded

The one use case worth writing out in full, because every invariant shows up in it.

PreconditionCorpus published for the resolved jurisdiction; actor authenticated or in an anonymous session.
Main flow1. Actor submits a question.  2. L3 resolves language, jurisdiction, as_of and intent.  3. If an explicit citation is detected, UC-02 runs instead and the flow ends.  4. Four candidate generators run in parallel; results fuse by RRF.  5. Cross-encoder reranks.  6. Gate evaluates against τ.  7. Context assembles whole provisions with validity and repeal state.  8. L4 generates a structured answer carrying citation identifiers.  9. Citation text is rendered from L2.  10. Verifier checks each claim against its cited span.  11. Answer streams to the client with per-claim provenance.  12. Audit record persisted.
A1 — gate failsAt step 6, no candidate clears τ. System returns an abstention naming what it searched, plus non-passing results explicitly labelled as unconfirmed. No generation occurs.
A2 — identifier unresolvedAt step 9, a citation identifier does not resolve. The block is dropped, the event logged as a defect, and the remaining answer is returned with a completeness note.
A3 — verification failsAt step 10, a claim is not entailed by its span. Below the drop threshold the block is removed; between drop and pass it is shown with a visible qualifier.
A4 — repealed law matchedRetrieved provision is repealed or was not in force at as_of. It is returned with a prominent status banner and never as the operative answer.
A5 — provider unavailableL4 provider port fails over; if all providers fail, the system degrades to UC-01 results plus stored explainers and says so.
PostconditionAn audit record exists sufficient to replay the answer exactly (INV-3). In anonymous mode, no record of query or answer content is written.
§3Domain
model

The law as data

Get this wrong and no amount of retrieval quality rescues the product. The model has to represent three things most legal databases do not: that a provision is a node in a tree, that its text changes over time, and that a citation points at a provision rather than at a page.

3.1Provision identity

Public, stable, human-readable, and resolvable without a database round trip for the common case.

pk:fed/act/1860-45/ch-XVI/s-302/cl-c
|   |    |         |        |     |
|   |    |         |        |     +-- clause      ProvisionKind, ordinal within parent
|   |    |         |        +-------- section     label preserved verbatim: 302, 337A, 365 A
|   |    |         +----------------- chapter     roman numeral as printed
|   |    +--------------------------- instrument  year-number, the gazette identity
|   +-------------------------------- kind        act|ord|order|rules|sro|notif|const
+------------------------------------ scope       fed|punjab|sindh|kp|balochistan|ict|ajk|gb

Stored as ltree.  Subtree query: path <@ 'fed.act.1860_45.ch_XVI'
                  Ancestor query: path @> 'fed.act.1860_45.ch_XVI.s_302.cl_c'

§8Modules

Module decomposition

Ownership is by layer, not by feature, so each person owns an interface they must keep stable rather than a screen they can change freely. That is what makes four people working in one repository tractable.

The one automated rule worth enforcing: an import-linter configuration in CI that fails the build if a package imports across a forbidden layer boundary. It is about twenty lines of configuration and it is the only thing that will keep the dependency graph in Figure 8 true six months from now.

§9Runtime
operations

Deployment and degradation

A single-node system with an honest availability target is more useful than a distributed one nobody can operate. What matters architecturally is not uptime but what the system does as pieces fail.

9.1The degradation ladder

Each rung names a component failure and the capability that survives it. Every rung is a code path that must be tested, not a hope.

FailureLostRetainedUser sees
LLM provider unreachableAnswers to questions outside the stored set, judgment summarisation, interview phrasingAll search, citation lookup, precedent lists, stored explainers, calculators, procedure guides — and every answer in the pre-generated answer tierA banner naming the degraded capability. Because answers were batch-generated and verified ahead of time, the head of the query distribution is unaffected by a provider outage.
Inference worker downDense retrieval, reranking, entailment verification → therefore all generation (INV-2 blocks ungated answers)BM25 search, citation fast path, whole-provision browsing, everything deterministicLexical search only, labelled as such. The system does not silently lower τ.
Database unreachableEverything server-sideThe entire offline pack on any device that has oneApp falls through to local pack automatically; web shows a status page.
Ingest worker downNew and amended law does not arriveAll servingNothing, until staleness exceeds the threshold — then a corpus-currency notice appears.
Object store unreachableSource PDF viewing, new document downloads, pack updatesAll text, all search, all answersSource-PDF links disabled; nothing else changes.
No client connectivityGeneration, precedent, drafting, anything requiring the serverFull statutory search and browse, stored explainers, offline calculatorsOffline mode, entered automatically and stated plainly.

The rule that makes this coherent

Degradation is always announced and narrower, never silent and approximate. The system may say “I can only search the text right now”; it may never quietly answer with a lower confidence bar. This follows directly from QA-2 and is why no failure path anywhere is permitted to lower τ, skip verification, or substitute an ungrounded answer.

9.3Observability requirements on every layer

  • Trace — one span per pipeline stage, carrying its scores. A retrieval trace without candidate scores is not debuggable, and most of the hard bugs in this system will be retrieval bugs.
  • Replay — INV-3 makes every answer reconstructible. This is the mechanism behind UC-16 and the only credible response to “the system told me the wrong thing.”
  • Corpus currency — per-source last-successful-fetch, exposed as a metric and surfaced in the UI when stale.
  • Gate telemetry — abstention rate by intent and language, tracked continuously. A sudden drop means τ is drifting or the corpus changed shape; a sudden rise means retrieval broke.
  • Cost per answer — a first-class metric, since QA-10 is an architectural target and not a footnote.

Appendix B — Architecture decision records

All twelve are accepted. Each has a one-line consequence that is checkable in code, which is what distinguishes a decision from a preference.

ADRDecisionDrivesCheckable consequence
ADR-1One Postgres for relational, vector, lexical and graphQA-10 QA-11No second datastore client library appears anywhere in nizam/. Chunk row and its vector are written in the same transaction.
ADR-1aHosting is a four-stage ladder, not a single choiceQA-3 QA-10 QA-11Stage 0 local Docker with the full corpus and every extension; stage 1 a managed free tier publishing federal statutes only (measured 248 MB against a 500 MB ceiling); stage 2 a self-hosted node once case law lands; stage 3 vertical then replicas. Real BM25 needs ParadeDB pg_search, which no managed host permits, so lexical retrieval sits behind ILexicalSearch and the tsvector fallback’s ranking delta is measured against the local baseline. Moving rungs changes a connection string, a bound implementation, and the published scope — nothing else. Sized in the capacity plan.
ADR-1fFull-scale target is a single self-hosted nodeQA-3 QA-8 QA-10Managed Postgres hosts the database, not the system: inference workers, ingest workers, the LaTeX sandbox and the staging filesystem still need a second host, and every query then crosses the public internet. One node runs all of it with pg_search available and the database on a loopback socket, at roughly a fifth of the cost. The self-hosted Supabase stack may run on top of it for the same developer surface without the extension lock-out. Sized in the capacity plan §5.2.
ADR-1gSchema is migrations in git; engine is a pinned imageQA-11The production database is built locally at full scale — every statute, judgment, embedding and index — on the same pinned Postgres image the server will run. Moving to the own-node target is then a pgBackRest restore rehearsed by the monthly drill, not a migration. A schema created by hand in a GUI is reproducible nowhere and is treated as a defect.
ADR-1dVectors stored binary-quantised as bit(1024)QA-3 QA-1032× smaller than float32 — 51 MB instead of 1,577 MB at full statutory scale. Safe only because a cross-encoder already reranks by reading provision text, so stage-1 dense retrieval need only preserve recall; candidates are over-fetched 10×. Ships only after an ablation reporting Recall@50 and NDCG@10 at float32, halfvec(384) and bit(1024); if binary costs more than two NDCG points after reranking, fall back to halfvec and narrow the corpus scope.
ADR-1ePublished corpus scope is a deployment parameterQA-10 QA-11The gate runner promotes instruments to the live index by scope tag. The same schema and migrations serve a 248 MB demo and a 10 GB pilot, so narrowing scope to fit a host is a configuration change and never a schema compromise.
ADR-1bTwo sync engines: signed one-way corpus, merged bidirectional user dataQA-9 QA-11Corpus patches are server-authored and signed, so no merge logic exists and the device is never a writer. User data syncs last-writer-wins on a server-assigned version with tombstones. Specified in document 08 §3.5.
ADR-1cOffline answers ship as verified artefacts, not as an on-device generatorQA-1 QA-9 QA-10L4 batch-generates and verifies answers to the head of the query distribution; they ship in a 12 MB pack tier with their citations and the provisions they depend on. A patch that amends a cited provision invalidates every dependent answer. Specified in document 08 §3.4.
ADR-2Fine-tune retriever and reranker; generation behind a provider portQA-3 QA-11A vendor SDK import appears only in generation/providers/. The reranker checkpoint is versioned in the eval harness.
ADR-3Text-layer extraction first; OCR is a fallback laneQA-4OCR runs only when the extractor reports low text confidence. Its invocation count is a metric.
ADR-4Direct cross-lingual retrieval, not a translation pipelineQA-6No translation call on the retrieval path. Bilingual NDCG gap measured on paired golden queries.
ADR-5Roman Urdu is a first-class input modeQA-6 QA-14The golden set contains a romanised stratum; the glossary alias index is a versioned artefact.
ADR-6Attributed generation with measured faithfulness, not a zero-hallucination claimQA-1 QA-2Verifier pass rate is published continuously. No marketing or academic text asserts impossibility.

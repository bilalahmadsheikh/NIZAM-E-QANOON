§1Extensions
& types

What the database must provide

Four extensions, each earning its place by making something structurally impossible rather than merely convenient. Any host that cannot supply them changes what this layer can guarantee, which is why the substitution is modelled rather than hidden.

ExtensionUsed forIf unavailable
vector (pgvector)Binary-quantised embeddings and HNSW indexes over themNo dense retrieval. There is no substitute; this one is non-negotiable
pg_search (ParadeDB)True BM25 with length normalisation over provision and paragraph textFall back to tsvector + GIN behind ILexicalSearch (§6). Ranking quality drops by a measured amount
ltreeProvision tree paths; subtree and ancestor queries without recursive joinsRecursive CTEs over parent_id. Correct but materially slower on deep trees
btree_gistThe exclusion constraint that makes overlapping validity intervals impossibleApplication-enforced temporal integrity, which is to say no integrity at all. This is the reason SQLite was rejected as a server engine
pg_trgmFuzzy matching for romanised Urdu aliases and misspelled act titlesExact matching only; Roman Urdu recall drops

CREATE EXTENSION IF NOT EXISTS pg_search;    -- ParadeDB BM25; shared_preload_libraries below PG17
CREATE EXTENSION IF NOT EXISTS ltree;
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- required by the EXCLUDE constraint in 2.3
CREATE EXTENSION IF NOT EXISTS pg_trgm;

source_sha256 is not decoration: it is how the ~48 duplicate documents measured in the federal corpus are detected, and how a re-scrape proves a source has genuinely changed before an ingest run is triggered.

2.2Provision — the citable unit

CREATE TABLE provision (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  instrument_id uuid NOT NULL REFERENCES instrument(id) ON DELETE CASCADE,
  parent_id     uuid REFERENCES provision(id) ON DELETE CASCADE,
  path          ltree NOT NULL,        -- fed.act.1860_45.ch_XVI.s_302.cl_c
  kind          provision_kind NOT NULL,
  label         text NOT NULL,         -- "302", "337A", "(c)", "Proviso" — verbatim
  heading       text,
  marginal_note text,
  ordinal       integer NOT NULL,      -- sort order within the parent
  CONSTRAINT uq_provision_path UNIQUE (path)
);

-- ON DELETE CASCADE on both foreign keys is the composition in the domain model:
-- a provision cannot outlive its instrument, a child cannot outlive its parent.

2.3Provision version — where temporal correctness is enforced

CREATE TABLE provision_version (
  id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  provision_id       uuid NOT NULL REFERENCES provision(id) ON DELETE CASCADE,
  validity           daterange NOT NULL,   -- '[1860-10-06,2005-01-01)' ; upper NULL = in force
  text_en            text,
  text_ur            text,
  text_normalised    text NOT NULL,
  operation          version_op NOT NULL DEFAULT 'original',
  amended_by_id      uuid REFERENCES instrument(id),
  amendment_note     text,                -- "Subs. by Act XLIII of 2016, s.3" — verbatim footnote
  extraction_conf    real,
  verified_by        text,
  verified_at        timestamptz,

  CONSTRAINT no_overlap EXCLUDE USING gist (
    provision_id WITH =,
    validity     WITH &&
  )
);

The four lines that carry INV-5

That exclusion constraint makes two overlapping validity intervals for the same provision impossible to insert. A buggy amendment resolver fails loudly at commit rather than quietly producing a corpus where section 302 has two simultaneous texts and a point-in-time query returns whichever the planner reached first. It is the single most important line in this schema, and it is the reason SQLite — which has no EXCLUDE constraint — was rejected as a server engine despite matching the mobile pack.

2.4Amendment events and cross-references

CREATE TABLE amendment_event (

  amending_instrument_id uuid REFERENCES instrument(id),
  target_provision_id    uuid REFERENCES provision(id) ON DELETE CASCADE,
  operation              version_op NOT NULL,

);

CREATE TABLE provision_xref (
  src_provision_id uuid NOT NULL REFERENCES provision(id) ON DELETE CASCADE,
  dst_provision_id uuid NOT NULL REFERENCES provision(id) ON DELETE CASCADE,
  raw_text         text NOT NULL,        -- "under section 304"

raw_note is retained unparsed forever. When the amendment grammar improves, every unresolved event can be reprocessed without re-reading a single PDF — and resolved = false rows are a queue, not a failure.

Correction to §4: the ltree GiST index does not work at corpus scale. §4 lists a GiST index on provision.path for “subtree and ancestor queries without recursive joins”. Once the corpus became append-only, retired revisions legitimately repeat their paths, and the duplicate-heavy history made the index pathological: writes first exceeded max_stack_depth, and with the ceiling raised they wedged the database mid-run.

It is replaced by provision_ancestor, an explicit ancestor closure answered by ordinary B-tree equality. Migration 0027 corrected its extent: closure is generated recursively from real parent_id edges, not from the three synthetic ltree labels that identify an observation. This removed 1,563,444 unreachable rows without touching canonical data. provision.path remains ltree and remains the canonical, immutable lineage; exact historical lookup is covered by uq_provision_instrument_path. Migrations 0017, 0018 and 0027.

Correction to §6: the write path is retire-and-append, not delete-and-rebuild. §6 describes one materialisation per document replaced in a transaction. Migration 0012 made document, instrument and block_assignment_set revision-bearing: is_active, supersedes_*_id, retired_at, verification_state. A re-run retires the previous revision and appends a new one, so a regression is diagnosable rather than lost.

Every current-state view and every audit query must therefore filter is_active. A query that reads the base tables directly counts every generation ever produced — which is a real defect this project shipped once and caught in review.

Active is still not the publication boundary. It means the newest evidentiary revision and deliberately includes quarantined material. Migrations 0030 and 0035–0040 require passed source evidence, canonical identity, complete printed contents, no pending S7 candidate, and no unresolved multi-instrument boundary. On 10 September 2026 the legal views contain 3,720 instruments, 300,137 provisions and 285,156 versions. Production retrieval must use these views; reviewers retain every active revision and archived proof of safely pruned superseded derived trees.

One observation can materialise several expressions. Migration 0040 replaces the old one-instrument-per-observation assumption with uniqueness on (source_observation_id, expression_ordinal). Each expression stores a guarded first/last source block and a versioned instrument_expression_manifest; one active assignment set still accounts for every source block exactly once. save_many() retires and appends the whole expression set atomically, so a partial split cannot publish.

Instruments are keyed on source_observation_id, not document_id: the same Act published on a federal and a provincial portal is two official observations of one work, and doc 03b §3 requires both to remain separately segmentable until identity resolution is reviewed.

§3Chunks
& vectors

Chunks store offsets, not text

A chunk is an index artefact with no independent existence. Storing its text would duplicate the entire corpus — 158 MB at statutory scale, 2 GB with judgments — for nothing, since the provision text is already stored and already indexed.

CREATE TABLE chunk (
  id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  version_id     uuid NOT NULL REFERENCES provision_version(id) ON DELETE CASCADE,
  seq            smallint NOT NULL,
  char_start     integer NOT NULL,     -- offsets into provision_version.text_normalised
  char_end       integer NOT NULL,
  context_prefix text NOT NULL,        -- act short title + chapter heading, ~80 chars
  embedding      bit(1024) NOT NULL,   -- binary-quantised; 136 bytes on disk
  CONSTRAINT ck_span CHECK (char_end > char_start),
  CONSTRAINT uq_chunk UNIQUE (version_id, seq)
);

Why bit(1024) is a column and not an expression index

pgvector’s documented binary-quantisation pattern keeps the full-precision vector in the table and indexes binary_quantize(embedding)::bit(n) as an expression, so the table still pays 4,104 bytes per row and only the index shrinks. We store the bits directly instead — 136 bytes per row — and do not retain the full-precision vector at all.

That is only safe because we never rescore inside the database. Precision is recovered one stage later by the cross-encoder, which reads the provision text, not any embedding. A system without a reranking stage could not make this trade; ours was built with one as the gate. The consequence for storage is 21.5 MB of chunk rows instead of 649 MB at full statutory scale.

Re-embedding is therefore a full rebuild of chunk rather than an in-place update — which is correct, because a new embedding model produces a differently-shaped space and mixing two generations in one index would be silently wrong. The rebuild is a TRUNCATE plus a batch pass, and it never touches provision_version.

4.1The two queries that must be fast

-- point-in-time provision read. Every client read goes through this shape.
SELECT p.path, p.label, p.heading, v.text_en, v.validity, i.status
FROM provision p
JOIN instrument i ON i.id = p.instrument_id AND i.published
JOIN provision_version v ON v.provision_id = p.id
                          AND v.validity @> $as_of::date      -- gist, INV-5
WHERE p.path <@ $subtree::ltree                            -- gist
ORDER BY p.path;

-- dense candidates with over-fetch, jurisdiction- and time-filtered
SELECT c.version_id, c.char_start, c.char_end
FROM chunk c
JOIN provision_version v ON v.id = c.version_id AND v.validity @> $as_of::date
JOIN provision p ON p.id = v.provision_id
JOIN instrument i ON i.id = p.instrument_id
                  AND i.published AND i.jurisdiction = ANY($juris)
ORDER BY c.embedding <~> $qbits::bit(1024)                 -- hamming, hnsw
LIMIT 500;                                                -- 10x over-fetch for 50 kept

As-built release correction: the conceptual queries above use published, but the current implementation has stronger evidence boundaries. Chunk creation and application reads must start from v_release_provision_version joined to v_release_provision and v_release_instrument; base-table active rows include retained S7 uncertainty. The second query filters and orders by an index, which is exactly the shape that used to over-filter in pgvector before iterative index scans landed. Verify the plan uses the HNSW index rather than falling back to a sequential scan whenever the jurisdiction filter is narrow — and raise hnsw.ef_search per session rather than globally.

§5Lexical
port

ILexicalSearch — two implementations, one benchmark

This is the seam that keeps the hosting decision reversible. No managed Postgres permits pg_search, so the fallback must exist, must work, and must have a measured quality cost rather than an assumed one.

class LexicalSearch(Protocol):
    def search(q: str, filters: Filters, k: int) -> list[Candidate]: ...

# implementation A — ParadeDB, true BM25 with length normalisation
SELECT id, paradedb.score(id) AS score
FROM provision_version
WHERE id @@@ paradedb.match('text_normalised', $q)
ORDER BY score DESC LIMIT $k;

# implementation B — portable, ts_rank_cd
SELECT id, ts_rank_cd(to_tsvector('english', text_normalised),
                        websearch_to_tsquery('english', $q), 32) AS score
FROM provision_version
WHERE to_tsvector('english', text_normalised) @@ websearch_to_tsquery('english', $q)
ORDER BY score DESC LIMIT $k;
-- normalisation flag 32 divides by (rank + 1); the closest ts_rank_cd gets to
-- BM25 length normalisation, and still materially different on long provisions
The benchmark is a required deliverable, not an optional experiment. Run it once on the local pg_search baseline before any managed host is considered.

8.1Row-level security

ALTER TABLE bookmark ENABLE ROW LEVEL SECURITY;
ALTER TABLE bookmark FORCE ROW LEVEL SECURITY;   -- applies to the table owner too

CREATE POLICY bookmark_owner ON bookmark
  USING (user_id = current_setting('nzq.user_id', true)::uuid)
  WITH CHECK (user_id = current_setting('nzq.user_id', true)::uuid);

-- the corpus is world-readable to the application role and writable only by the
-- publisher role; there is no policy that lets a user session write to it at all
REVOKE INSERT, UPDATE, DELETE ON instrument, provision, provision_version,
                                  chunk, citation_edge FROM app_role;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_role;

FORCE ROW LEVEL SECURITY matters more than it looks: without it, policies are bypassed for the table owner, which is exactly the role a migration or a careless connection string is likely to use. And the corpus grants are the database-level expression of “there is no second write path” — the application role physically cannot publish.

8.2Sync, server side

-- corpus sync: one-way, signed. The client is never a writer.
SELECT patch_id, from_version, to_version, sha256, signature, url
FROM pack_patch
WHERE from_version >= $client_version AND tier = ANY($installed_tiers)
ORDER BY from_version;

-- user-data sync: bidirectional, last-writer-wins on a server-assigned version
SELECT * FROM bookmark
WHERE user_id = $uid AND version > $cursor
ORDER BY version LIMIT 500;                  -- tombstones included, filtered client-side

The cursor is the sequence value, never a timestamp. Device clocks are wrong often enough that a timestamp cursor silently loses writes, and the failure is invisible until a user notices a bookmark they deleted has returned.

Recovery

  • pgBackRest to R2 — weekly full, daily incremental, continuous WAL archive, fourteen-day window. This is the point-in-time recovery that Supabase charges $100/month for.
  • Monthly restore drill into a scratch container, with the golden set run against the restored copy. A backup nobody has restored is a hypothesis.
  • The corpus is rebuildable from R2 blobs plus the scraper manifests plus the migrations, without any backup at all. That is the deepest safety property in the system: the database is derived data, and only user content is genuinely irreplaceable — which is also why user tables are tiny and easy to protect separately.

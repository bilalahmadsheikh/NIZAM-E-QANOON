§1Machine
or job

There is one machine and one job

The distinction matters more than any spec. Parsing the corpus is a job that runs a handful of times in the project’s entire life. Every developer machine restores the result instead — and never opens a PDF at all.

Corrected from v1.0, which framed the build machine as a per-developer profile. It is not: it is a few hours of rented compute, three or four times ever.

1.1How everyone else gets the corpus

Because the Postgres image is digest-pinned and identical everywhere, the corpus ships as a physical pgBackRest backup rather than a logical dump. A physical restore is a file copy: the indexes arrive already built, so there is no HNSW rebuild on the receiving machine.

CorpusBackup sizePhysical restorepg_restore instead
Statutes only~280 MB< 1 min~4 min — rebuilds every index
With judgments~3.5 GB~6 min~50 min — the HNSW build dominates

This is also why the restore drill in §7 is not overhead: the procedure that gives a new developer a corpus is the same procedure that recovers production, so it gets exercised weekly rather than discovered during an incident.

Content-hash gating is what keeps the steady state small: a re-scrape that finds no change does no work, so the ingest worker in production is a cron job sized in hundreds of megabytes, not the eight-worker pool the build job uses.

The one hardware rule that still matters

Keep pgdata on the internal NVMe, inside the Linux filesystem. On Windows that means inside WSL2, never on /mnt/c — the 9p bridge is roughly ten times slower for many small files, and every index operation is random I/O. Source documents can live on external storage; they are read sequentially, once, by a job you are renting a machine for anyway.

A 16 GB laptop runs the full corpus, including judgments

The 10 GB judgment database sits on disk, not in memory. With shared_buffers at 2 GB plus whatever the OS caches, roughly a third of it stays hot — and the rest falls through to NVMe at about 100 microseconds a page. Retrieval p95 rises from around 190 ms to perhaps 350 ms.

That is a latency difference, not a quality difference. Nothing about ranking, grounding, citation accuracy or abstention depends on how much of the index is cached. You would notice it while developing; no test would fail because of it.

§4Postgres
config

Configuration, computed

Default Postgres is tuned for a shared server from a decade ago and will make every number in this document wrong. These values are derived from the profile, not copied from a blog post.

# postgresql.conf — developer machine, 16 GB host, ~3 GB budget for Postgres

shared_buffers                  = 2GB      sized to the working set, not to a share of host
                                             RAM. The statutory index hot set is ~400 MB
effective_cache_size            = 8GB      planner hint: what the OS is likely caching.
                                             Not an allocation — it only shapes plans
work_mem                        = 64MB     per sort/hash node, per parallel worker.
                                             64MB x 4 workers x 8 conns = 2GB worst case
maintenance_work_mem            = 1GB      only matters on the build job; a developer
                                             machine restores indexes rather than building them
max_worker_processes            = 16
max_parallel_workers            = 4        = physical cores
max_parallel_workers_per_gather = 4
max_parallel_maintenance_workers= 4        parallel HNSW build — the single biggest
                                             win on index build time
random_page_cost                = 1.1      NVMe. Leaving this at 4.0 makes the planner
                                             avoid index scans it should be using
effective_io_concurrency        = 200      NVMe queue depth
wal_buffers                     = 64MB
max_wal_size                    = 8GB      bulk load; lower to 2GB for normal operation
checkpoint_timeout              = 15min
checkpoint_completion_target    = 0.9
jit                             = off      hurts more than it helps on our query shapes

# extensions
shared_preload_libraries        = 'pg_search'   required only below PG 17; harmless on 17

# session-level, set by the retrieval layer rather than globally
hnsw.ef_search                  = 100      raise for recall, lower for latency.
                                             Cluster-wide changes need ALTER SYSTEM +
                                             pg_reload_conf(), not ALTER ROLE

Bulk-load profile

During a full corpus ingest, switch to a second config: maintenance_work_mem = 8GB, max_wal_size = 16GB, autovacuum = off on the four large tables, synchronous_commit = off. Then re-enable autovacuum, run ANALYZE, and build the HNSW and BM25 indexes last. Building indexes before the load is the most common way to turn a 45-minute index build into a six-hour one.

One rented hour, under a dollar, once. The judgment embedding pass is the only workload in the entire project that justifies a GPU, and it is a batch job that runs when the corpus lands and again only when the embedding model changes. Rent a consumer card by the hour, mount the corpus, write vectors back over the network, and destroy the instance. Buying a GPU for this would be a category error — and note that the same conclusion holds in production, where ADR-1f keeps the GPU node off every request path.

§6Bootstrap

The build job, start to finish

This sequence runs on the rented machine, three or four times in the project’s life. Every stage writes its state to the database, so an interrupted run continues rather than restarting — which matters because stage 3 on the full corpus runs for two hours. A developer setting up for the first time runs steps 0 to 2 and then restores a backup instead of steps 3 to 5.

# 0 — prerequisites, once
docker compose version                       v2, and set the Desktop memory cap explicitly
uv --version ; node -v ; git lfs install

# 1 — bring up the stack and create the schema
git clone <repo> && cd nizam
cp .env.example .env                         set POSTGRES_PASSWORD, R2 keys optional locally
docker compose up -d postgres minio
uv run alembic upgrade head                  the schema exists only because of this
uv run python -m nizam.ops.verify_extensions fails loudly on a version mismatch

# 2 — fetch model artifacts and convert once
uv run python -m nizam.ops.fetch_models --int8
docker compose up -d inference api

# 3 — ingest, resumable at every stage
uv run python -m nizam.corpus.run --source federal   --workers 8
uv run python -m nizam.corpus.run --source provincial --workers 8
uv run python -m nizam.corpus.run --source judgments  --workers 8   build job only

# 4 — embed. CPU for statutes; rent a card for judgments
uv run python -m nizam.index.embed --scope statutes            ~53 min CPU
uv run python -m nizam.index.embed --scope judgments --remote  ~53 min on a rented GPU

# 5 — build indexes last, with the bulk-load config still active
uv run python -m nizam.index.build --hnsw --bm25 --analyze

# 6 — prove it
uv run pytest tests/integration
uv run python -m nizam.evals.run --set golden --report
uv run python -m nizam.ops.backup --to local && uv run python -m nizam.ops.restore --check
§7Parity

Proving the local build is production

The whole point of ADR-1g is that what you build locally is the production database, so moving it is a restore rather than a rebuild. These are the checks that keep that true.

CheckHowFails when
Schema comes only from migrationsCI runs alembic upgrade head against an empty database, dumps the schema, and diffs it against a committed golden schema fileSomeone created an index in pgAdmin. This is the most common and most damaging drift
Extension versions pinnedA migration asserts pg_search, vector and ltree versions and raises on mismatchA newer image silently changes ranking or index format
Image digest pinnedCompose references @sha256:…, not :latestlatest moved and two developers now disagree about BM25 scores
Collation identicalAssert lc_collate and lc_ctype in the same migrationA different collation changes index ordering and text comparison — silent, and genuinely nasty to diagnose
Postgres major version identicalAssert server_version_num rangeA physical restore across major versions is impossible; you would need a dump
Backup round-tripsMonthly: restore the local repository into a scratch container and run the golden set against itThe backup was never valid. Better to learn this on a laptop
Evaluation is reproducibleGolden-set NDCG@10 and faithfulness recorded per commit; CI blocks regressionsRetrieval quality changed and nobody noticed which change did it

The rule, stated once

pgAdmin4 is a viewer. Every schema object — table, index, constraint, extension, role, policy — is created by a migration file in git and by nothing else. If the answer to “how do I recreate this on the server?” is anything other than “run the migrations”, the local environment has stopped being production and the move in document 09b stops being a two-hour restore.

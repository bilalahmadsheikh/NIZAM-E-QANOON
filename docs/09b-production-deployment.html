What the system actually consumes

Sizing starts from work per request, not from a vendor tier. The conclusion is unintuitive and it drives every choice below: this system is bound by memory and disk, not by CPU.

The reranker must be small, and that is a design decision, not a compromise

A 560M-parameter cross-encoder reranking 50 pairs costs roughly 3.3 core-seconds per query on CPU — nine times the entire rest of the pipeline, and enough to make CPU the binding constraint at even modest load. A fine-tuned MiniLM-class cross-encoder does the same job at about 0.15 core-seconds. Since ADR-2 already commits us to fine-tuning the reranker on our own golden set, training the small one is strictly better: we get the domain adaptation and a twentieth of the latency. Benchmark both during the ablation; ship the small one unless the large one wins by more than it costs.

Source documents do not live on the server

The 40 GB of judgment PDFs sits in R2, not on the production disk — the server holds the extracted, structured corpus and nothing else. That single correction takes the disk requirement from 130 GB to under 50 GB and puts several cheaper machines back on the table.

1.4Trading latency for memory, deliberately

The instinct that a little more latency should buy a lot less memory is correct, and it is worth stating as an explicit dial rather than discovering it under pressure. HNSW traversal is random-access: an uncached page costs roughly 100 µs on NVMe, and a query touches on the order of a thousand of them in the worst case.

Estimated p95 for a full grounded answer at pilot load. The corpus is 10 GB; what changes is how much of it stays hot.

Every row answers identically. Ranking, grounding, citation accuracy and abstention are properties of the index and the pipeline, not of how much of the index is resident. Memory buys latency; it does not buy quality. The QA-8 budget is 4 seconds at p95, and even the bottom row spends a tenth of it.

You run out of money before you run out of server

At 250,000 monthly active users the machine costs about €40 and the LLM calls cost roughly $2,400 a month — sixty times more. At 500,000 the server is still one box and the model bill is near $5,000.

So the honest capacity answer is: a single €21–40 VPS comfortably carries 50,000 to 100,000 monthly active users, and does not become the binding constraint until somewhere past 250,000. Long before that, the questions that matter are how much of the answer traffic the offline answer tier and the semantic cache can deflect, and whether the paid advocate tier covers the model bill. Both are product decisions, not infrastructure ones.

What to do at each ceiling, in order

  1. Cache harder. Widen the semantic response cache and mine production logs to expand the answer tier. Deflection is worth more than hardware at every load point above pilot.
  2. Add RAM, not cores. Cache pressure shows up long before CPU does.
  3. Add PgBouncer. Connection exhaustion is the first hard wall, and it arrives around 100,000 MAU.
  4. Partition the audit log monthly and archive old partitions to R2.
  5. Split the database onto its own host (§3), private network, no public IP.
  6. Add a read replica for search and public pages. Only here does the architecture need a second serving node.

If you want x86 or headroom: CAX41 at €40.99 gives 32 GB; EX44-1-LTD at €57.30 gives 64 GB and dedicated cores. Neither is required by the sizing in §1 — both simply remove memory from the list of things you ever think about again, which at these prices is a defensible purchase.

The floor: Contabo Performance VPS 4 (4 vCPU, 8 GB, 150 GB NVMe, €13.50) still runs the whole system at roughly 450 ms p95. Tight, but not a mistake.

At scale, the server is a rounding error

Fifty thousand monthly active users cost about €21 of compute and roughly €690 of per-request services. Which means the two most valuable cost controls in this architecture are not infrastructure decisions at all — they are the offline answer tier and the semantic response cache, both of which remove LLM calls entirely. Every point of deflection is worth roughly $8 a month at this volume. That reframes the answer tier from an offline convenience into the primary lever on unit economics, and it is the strongest argument yet for mining and pre-generating aggressively.

The second lever is SMS. Send an OTP on signup and on new-device sign-in only, never on every session, and the line drops by more than half.

§6Operations

The minimum that must exist

AreaStandard
BackuppgBackRest to R2 — weekly full, daily incremental, continuous WAL archive. Fourteen-day recovery window. This replaces the $100/month managed PITR add-on and is strictly more configurable
Restore drillMonthly, on a scratch container, with the golden-set evaluation run against the restored copy. A backup that has never been restored is not a backup, and the drill doubles as the rehearsal for the migration in the capacity plan §5.3
DeploysMigrations run before code. Compose file references image digests, never :latest. Every deploy tagged; rollback tested at least once per phase
UpgradesMinor Postgres monthly during a stated window. Major annually, rehearsed on the laptop first with a dump-and-restore since a physical restore cannot cross major versions
MonitoringLatency, traffic, errors, saturation — plus four domain signals: corpus currency per source, gate abstention rate, verifier pass rate, and cost per answer
AlertingDisk > 80%, backup failure, WAL archive stalled, p95 breach sustained 10 minutes, abstention-rate shift. Route to one person on a rota, not to a channel nobody watches
SecurityFirewall default-deny; SSH keys only, no password auth; unattended security upgrades; fail2ban; database bound to localhost or the private vSwitch only; secrets in a file with 0600, never in the compose file
RunbooksFour written before launch: restore from backup, rotate a leaked credential, roll back a bad deploy, and recover a failed corpus publish

6.1What a dedicated server obliges that a cloud instance does not

Hetzner’s dedicated line has no hypervisor beneath it, which is most of why it is fast and cheap. Three consequences worth planning for: there is no instant snapshot, so pgBackRest is the only recovery path and must genuinely work; there is no live resize, so a capacity change means provisioning a new machine and restoring; and hardware can fail in a way a cloud instance abstracts away, so the RAID 1 pair and the off-box backup are both load-bearing rather than belt-and-braces. Budget half a day for the initial hardening and accept that the restore drill is not optional.

1.1OCR is not a pillar — it is an edge case

All four documents treat OCR as a headline workstream: Tesseract 5 for English, UTRNet for Nastaliq, an entire "Aim 2". The measurement says ~96% of the corpus already carries a clean, extractable text layer. Here is a verbatim pdftotext -layout extraction from the Pakistan Penal Code, untouched:

provisions of this Chapter be__

                  (a) punished with death as qisas

                  (b) punished with death for imprisonment for life as ta'zir having regard to the facts
                           and circumstances of the case, if the proof in either of the forms specified in
                           section 304 is not available or

                  (c) punished with imprisonment of either description for a term which may extend
                           to twenty-five years, where according to the Injunctions of Islam the
                           punishment of qisas is not applicable 2[:]

2Subs. by Act XLIII of 2016, s.3.

         1[Provided that nothing in clause (c) shall apply where the principle of fasad-fil-arz is

Read what is in there: section number, section heading, body, lettered clauses with real indentation, a proviso, and numbered footnote markers bound to amendment provenance — Subs. by Act XLIII of 2016, s.3. That last part is the most valuable structured signal in the entire corpus and no proposal mentions it.

Consequence: OCR drops from a pillar to a ~150-PDF fallback path (mostly Balochistan). The engineering weeks that frees go into structural parsing and case law, which are where the project actually lives or dies.

1.3The critical gap: there is no case law

Aim 7 — the citation network, arguably the most defensible thing in the whole proposal — depends entirely on Supreme Court and High Court judgments. We have zero. Statutes without precedent gives you a better Pakistan Code; statutes with precedent gives you something PakistanLawSite charges for and Harvey cannot do.

Start this week

Judgment acquisition is the long pole: five High Courts plus the Supreme Court plus the Federal Shariat Court, each with a different site, each rate-limited, and collection realistically takes six to ten weeks of wall-clock time. Nothing downstream of it can start until it does. It should begin before a single line of API code is written.

Copyright line to hold: judgments published on official court websites are public records and are fine. PLD / SCMR / YLR headnotes and editorial matter are Oratier/PLD Publishers copyright — we never scrape those. We may cite the reporter reference (PLD 2016 SC 1) as a factual identifier; we may not reproduce their prose.

§2Departures

Twelve places I am changing the plan

The proposals were written to be persuasive. This is the version written to be built. Each row is a deliberate departure with the reasoning attached — take them individually, argue any of them.

#Proposal saysWe doWhy
D1Qdrant + Supabase Postgres, dual databaseOne Postgres. pgvector HNSW for dense, pg_search (ParadeDB) for real BM25, ltree for provision trees.Our whole corpus is ~1.5 M chunks. Qdrant earns its keep past ~10 M vectors. Two stores means two write paths, eventual inconsistency between a chunk and its vector, two backup regimes, and a second bill — for zero measurable gain. One store gives us transactional re-indexing: amend a section and its text, vector, and FTS entry move in the same commit.

§4Corpus
the moat

The corpus layer

Every model we use is a commodity available to anyone. A correctly segmented, version-tracked, cross-referenced, precedent-linked corpus of Pakistani law is not. This layer is the only thing in the system a competitor cannot buy, and it should get a disproportionate share of our effort.

4.1The canonical unit is a Provision, not a chunk

Chunks are a disposable index artefact. Citations, bookmarks, generated documents, offline packs, deep links and precedent edges all point at a provision with a stable identity:

pk:fed/act/1860-45/ch-XVI/s-302/cl-c
|   |    |       |       |     |
|   |    |       |       |     +-- clause (c)
|   |    |       |       +-------- section 302
|   |    |       +---------------- chapter XVI
|   |    +------------------------ Act XLV of 1860 (PPC)
|   +----------------------------- instrument type
+--------------------------------- jurisdiction: federal

Stored as a Postgres ltree path so subtree queries (“everything under Chapter XVI”) and ancestor queries (“which section does this proviso belong to?”) are index-backed one-liners. Re-chunk the corpus five times and not one stored citation breaks.

That last line matters: a Postgres exclusion constraint makes overlapping validity intervals for the same provision impossible to insert. Temporal correctness becomes a schema property rather than something we hope the ingest code remembers.

4.3The ingestion pipeline

Seven stages, each idempotent, content-addressed by the source SHA-256, individually resumable, and each writing a row that records what it did. Re-running stage 4 on 4,700 documents must be a normal Tuesday, not an incident.

What each stage actually does

StageWorkHard parts
1 fetchScrape, hash, store the byte-exact original in R2, record provenance URL and timestampAlready built and good — the existing scrapers have manifests, SHA-256, and resume. Extend to judgments and gazettes.
2 extractLayout-aware extraction preserving x/y position, font, size, indent depth, page boundariesUse PyMuPDF, not pdftotext. We need coordinates to detect footnote zones and indent levels. Text-layer confidence check routes ~150 scanned docs to the OCR lane.
3 normaliseStrip repeated headers/footers by positional recurrence; fix __ to em-dash; recover Urdu glyph runs; Unicode NFCPage furniture must be detected statistically (same text at same y across pages), not by regex — formats vary per province.
4 segmentBuild the provision tree from numbering grammar plus indentation plus font weightThe hardest stage. Pakistani numbering includes 302, 337A, 337Z, 365 A (with a space), 184(3), roman chapters, and schedules with their own numbering. Grammar-based parser with a per-instrument override table.
5 enrichBind footnote markers to their text; parse Ins./Subs./Omitted by ... into amendment events; extract cross-references and defined termsThe footnote apparatus is the gold seam. Markers are glued to adjacent characters (2[:]) so binding is positional, not textual.
6 versionResolve amendment events against the amending instrument dates; build validity intervals; propagate repealAmending acts must themselves be in the corpus and dated. Circular and retrospective amendments need a resolution order. Unresolvable cases are flagged, never guessed.
7 indexChunk provisions with parent-heading context, embed, write vectors, BM25 tsvector, and citation edges — all in one transaction per instrumentChunking respects provision boundaries: never split a section mid-clause, always prepend act title and chapter heading so a chunk is self-describing.

Quality gates — the definition of “ingested”

A document is not published to the live index until it passes all of these. Anything that fails goes to the curation queue with the failing gate named.

  • Coverage — concatenated provision text reconstructs ≥98% of normalised source characters. Catches dropped pages and swallowed sections.
  • Sequence — section labels are monotonic within their chapter, accounting for letter suffixes and omissions. Catches mis-splits.
  • Table-of-contents reconciliation — most Pakistan Code PDFs carry a full TOC. Parse it independently and diff against the parsed body. This single gate catches the majority of segmentation errors for free.
  • Cross-reference resolution — ≥95% of internal references resolve to an existing provision. Catches numbering errors.
  • Amendment resolution — every footnote citing an amending instrument resolves to an instrument in the corpus, or is flagged.
  • Duplicate detection — SHA-256 collision against a different title raises a review item (we have ~48 of these already).
  • Spot check — 5 random provisions per instrument rendered side-by-side with the source page for human sign-off on first ingest.

4.4Judgments and the citation graph

Same pipeline, different segmentation target: judgments split into numbered paragraphs, which are the citable unit for precedent, plus a header block (court, bench, judges, case number, date, parties, counsel) and a disposition.

judgment
  court SC|LHC|SHC|PHC|BHC|IHC|FSC, bench[], judges[], decided_on
  case_no, neutral_citation, reporter_refs[]  "PLD 2016 SC 1" as identifier only
  parties_raw, parties_redacted, subject_tags[]
  disposition allowed|dismissed|partly_allowed|remanded|disposed

judgment_paragraph
  judgment_id, para_no, text, role facts|arguments|reasoning|holding|order

citation_edge          the graph — recursive CTEs, no Neo4j needed
  src (judgment_paragraph), dst (provision | judgment)
  treatment cites|applies|interprets|follows|distinguishes|doubts|overrules
  confidence, extraction_method regex|model|human, verified_by

Extraction is two-pass. A citation grammar (high precision, moderate recall) finds the references; a model classifies the treatment from the surrounding paragraph. Treatment classification is the part that can be wrong, so it carries a confidence score and never renders as a bare assertion — the UI shows the paragraph that produced it so a lawyer can judge for themselves.

Why this is the defensible piece

Anyone can put statutes behind an embedding model in a weekend. A verified graph of how the Supreme Court has treated each provision, with paragraph-level anchors and point-in-time validity, takes a year and cannot be shortcut. It is also what turns a citizen tool into something a working advocate will pay for.

§5Retrieval

Retrieval, stage by stage

Retrieval quality sets the ceiling on everything downstream. A perfect generator on bad context produces a confident wrong answer; a mediocre generator on perfect context produces a useful one.

5.1Stage 0 — query understanding, before any model runs

SignalMethodEffect on retrieval
Explicit citationGrammar over the Pakistani citation space: s.302 PPC, section 9(c) CNSA, Art 184(3), PLD 2016 SC 1, 2019 SCMR 1, SRO 745(I)/2023Direct fetch. Bypasses the entire pipeline. Deterministic, ~5 ms, 100% precision.
LanguageScript detection plus a romanised-Urdu classifierSelects normalisation path and answer language. Roman Urdu goes through transliteration expansion.
JurisdictionUser profile, then query cues (“in Lahore”, “Sindh tenancy”), then default federalHard filter. Punjab rent law and Sindh rent law are different statutes; returning the wrong province is a wrong answer, not a near miss.
TemporalDate expressions; default as_of = todayFilters provision_version validity intervals.

5.2Stage 1 — four candidate generators in parallel

  • BM25 over provision text, heading, marginal note, and act title, with heading and title boosted. Real BM25 via ParadeDB pg_search, not ts_rank_cd — the length normalisation matters when provisions range from one line to three pages.
  • Dense over provision chunks. Start with an off-the-shelf multilingual encoder (BGE-M3 class: 8k context, Urdu and English in one space, dense + sparse + multi-vector from one model). Fine-tune it on our golden set in phase 2 — this is contribution #1.
  • Definition expansion — if a query term matches a term defined in a candidate act, pull the defining provision. Legal texts define their own vocabulary and the definition is frequently the answer.
  • Graph expansion — pull provisions cross-referenced by the top lexical hits. Ask about s.302 and you need s.299 (definitions), s.304 (proof), s.311 (fasad-fil-arz). No embedding model retrieves those; the reference graph does, for free.

Recall target: ~150 candidates. Optimise this stage for recall only — precision is the reranker’s job.

5.3Stage 2 — fusion by reciprocal rank

Reciprocal Rank Fusion, not score normalisation. BM25 scores and cosine similarities are not commensurable, and any weighting we hand-tune between them will be overfitted to whatever queries we happened to test. RRF uses only rank position, needs no tuning, and is robust when one retriever fails badly on a given query.

score(d)  =  sum over retrievers r  of   1 / ( k + rank_r(d) )      k = 60

5.4Stage 3 — cross-encoder rerank

A multilingual cross-encoder (bge-reranker-v2-m3 class, ~560M) scores each (query, provision) pair jointly. At int8 via ONNX Runtime this runs ~40–60 pairs/second per CPU core, which is fine at our QPS; it moves to a GPU worker when it stops being fine.

This is where our fine-tuning budget goes. Training a reranker on a few thousand labelled Pakistani legal query–provision pairs is cheap (hours on a rented 4090, well under $20), gives a large and directly measurable NDCG@10 gain, and is a far more defensible research contribution than another LoRA on an 8B chat model.

5.5Stage 4 — the gate

Two conditions, both calibrated on the golden set rather than guessed:

  • Absolute threshold — the top reranker score must exceed τ, chosen for a target precision (start at 95%) on held-out queries.
  • Coverage — for multi-part questions, each identified sub-question needs at least one passing provision, or the answer is partial and says so.

Below threshold, the system abstains with a specific message and offers the nearest non-passing results as “possibly related, not confident” — visibly separated from an answer. Abstention rate is a headline metric we publish, not a failure we hide. A system that never abstains is a system that is guessing.

5.6Stage 5 — context assembly

Never hand the model a half-section. Assembly expands each passing chunk to its full parent provision, then attaches the act short title, chapter heading, in-force dates, and any repeal or amendment warning. Deduplicates overlapping provisions, orders by statutory sequence rather than score (a model reads law better in its own order), and budgets tokens with the highest-scoring material protected from truncation.

5.7Roman Urdu, concretely

The mechanism is a normalisation table plus an alias index, not a model:

user types   "mje talaq k baad bachon ki custody chahiye"
normalise   mujhe talaq ke baad bachon ki custody chahiye
alias hits  talaq   → divorce, dissolution of marriage  (DMMA 1939, MFLO 1961 s.7)
             custody → hizanat, guardianship, custody of minors
                        (Guardians and Wards Act 1890 ss.7,17,25)
retrieve    English corpus, jurisdiction-filtered
answer      Urdu prose + English statutory text shown verbatim alongside

The alias index is a curated legal glossary: each concept maps a set of Urdu, romanised-Urdu (with spelling variants), and English legal terms onto the provisions that govern it. Perhaps 400–600 entries covers the overwhelming majority of citizen queries. It is hand-built, cheap, deterministic, and it is the single highest-leverage accessibility artefact in the project.

§6Generation
& grounding

Generation and the grounding contract

6.1The model is behind a port, always

One interface, several implementations, chosen per request by cost and difficulty. We never write provider-specific code outside an adapter.

class LLMProvider(Protocol):
    def complete(prompt, schema, max_tokens, cache_key) -> StructuredAnswer
    def stream(...) -> Iterator[Delta]

routing
  lookup / explain   → hosted small model, cached system prompt   cheapest path
  scenario / draft   → hosted reasoning-tier model
  sovereign / demo   → self-hosted open weights (vLLM), LoRA-tuned
  offline            → no generation; retrieval and stored explainers only

The self-hosted path is not decoration. It carries the FYP’s fine-tuning requirement, it is the answer to any data-sovereignty question from a government or institutional user, and it gives the thesis a genuine hosted-versus-tuned-open-weights comparison on the same benchmark — a better chapter than “we fine-tuned it and it worked.”

6.2Structured output, never prose

The model emits a validated object. It references provisions by identifier; it never writes a section number, a case citation, a date, or a URL.

{
  "abstain": false,
  "blocks": [
    { "text": "Intentional murder is punishable by death or life imprisonment.",
      "cites": [{ "provision": "pk:fed/act/1860-45/s-302/cl-a", "span": [0, 84] }] },
    { "text": "Where the proof required for qisas is unavailable, the court may
               instead impose ta'zir.",
      "cites": [{ "provision": "pk:fed/act/1860-45/s-302/cl-b", "span": [12, 190] }] }
  ],
  "caveats": ["Sentencing depends on facts the court finds proved."],
  "followups": ["What is the difference between qisas and ta'zir?"]
}
  • Every block carries at least one citation. A block without one is dropped before rendering — a schema rule, not a prompt request.
  • The renderer substitutes citation text from the database using the identifier. If the identifier does not exist, the block is dropped and the event logged. Fabricated citations are structurally unreachable.
  • Spans point into the retrieved provision text, which is what makes the next stage possible.

6.3The entailment verifier

For each block, check that the cited span actually supports the claim. Three tiers, chosen by cost and stakes:

TierMethodCostUsed for
CheapLexical and numeric overlap: every number, date, duration and monetary amount in the claim must appear in the span~0 msEvery block. Catches the most damaging error class — wrong sentence lengths and wrong fines.
StandardCross-lingual NLI model (mDeBERTa-xnli class), span as premise, claim as hypothesis~30 msEvery block. Below threshold, the block is flagged rather than dropped, and shown with a visible qualifier.
StrictSecond model call as adversarial judge, prompted to refute~$0.001Blocks that touch criminal liability, limitation periods, or anything time-barred. Also the full evaluation run.

The measured pass rate of this verifier is our faithfulness number. It is computed continuously in production, not once for the thesis.

6.4What the model is forbidden to do

  • Produce a section number, article number, case citation, SRO number, statute date or URL. All of these are rendered from database records.
  • Answer when the gate abstained. There is no fallback to general knowledge — the code path does not exist.
  • Recommend a course of action in the user’s own matter. The register is “the law provides X”, never “you should do X.” This is the Legal Practitioners and Bar Councils Act line, and it is enforced at prompt level and checked by a classifier on output.
  • Present a translation of statutory text as the statutory text. Urdu output is explanation; the English provision is always shown verbatim beside it.

6.5Cost control

  • Prompt caching on the static system prompt, schema and few-shots — roughly a 90% reduction on that portion of every request.
  • Semantic response cache — the same question in different words, same jurisdiction, same as_of, hits a cached answer. Legal queries are heavily long-tailed but the head is very heavy: “what is the punishment for theft” will be asked thousands of times.
  • Precomputed explainers — a plain-language explanation of every significant provision, generated once in batch and stored. Most citizen lookups then need zero live inference, and these ship in the offline pack too.
  • Fast path — explicit-citation queries never touch a model at all.

The product surfaces

Four things sit on top of the corpus and the pipeline. Each is separable, each is independently valuable, and each has a different failure mode to design against.

7.2The document factory

The architecture the proposals describe is correct and I would keep it: AI conducts the interview, deterministic code selects the clauses. A model must never choose which clause enters a legally operative document. Four stages:

  1. Interview — a schema-driven dialogue. The document type defines required and conditional fields; the model handles phrasing, clarification and validation, but the field list is code. Every answer is typed and validated (CNIC format, dates, amounts, jurisdiction).
  2. Clause selection — a rule table keyed on document type, province, and the interview answers. Rules cite the statute that requires each clause (Stamp Act 1899, Registration Act 1908, Transfer of Property Act 1882, the relevant provincial rent ordinance). Fully auditable; every clause in a generated document can be traced to the rule and the statute that put it there.
  3. Stamp duty and fee computation — per-province, per-instrument, deterministic, versioned by date. Genuinely useful, entirely non-AI, and it is what makes the output usable rather than decorative.
  4. Typeset — Jinja2 into LaTeX, compiled by pdflatex in a sandboxed container, with correct margins for stamp affixation, witness blocks, and page numbering. Bilingual documents use XeLaTeX with a Nastaliq font.

The one thing to get right here

Never let a generated document imply it has been reviewed. Every output carries a visible provenance block: which template version, which clause rules fired, which statute each clause rests on, and an unambiguous statement that it has not been settled by an advocate. A rejected document is a bad day; a document that costs someone their property because it looked official is the end of the project.

Template set, in build order: affidavit (general) · rent agreement, residential · rent agreement, commercial · legal notice · general power of attorney · special power of attorney · sale agreement for immovable property · employment contract · NDA · partnership deed · will · succession-certificate application · bail application · consumer complaint. Start with three, get them reviewed by a practising advocate, then scale — template count is a poor proxy for value and a good proxy for liability.

7.3Procedure — the deterministic layer

Underrated in all four proposals. These features involve no generative AI, cannot hallucinate, and are what actually gets a citizen from “I know the law” to “I did the thing.”

  • Limitation calculator — the Limitation Act 1908 schedule encoded as data. Enter the cause of action and its date, get the deadline and the article that governs it. Missing a limitation period is one of the most common and most catastrophic self-representation errors, and this is a pure lookup table.
  • Forum finder — which court, which district, what pecuniary limit, what territorial jurisdiction. Encoded from the CPC and provincial civil courts ordinances.
  • Court fee calculator — Court Fees Act 1870 plus provincial amendments, by suit value and relief type.
  • Step-by-step guides — expert-authored, versioned, each step citing its statutory basis, with verified official links stored as data and health-checked weekly. Never model-generated.
  • Document checklists per procedure, exportable.

Accessibility, seriously

National literacy is around 60%, and legal literacy far below that. Two features do more for reach than any model improvement:

  • Voice input and output in Urdu. A user who cannot comfortably read can speak a question and hear the answer. This is the difference between serving the top decile of the target population and serving the target population.
  • A reading-level control on explanations — the same grounded content, rendered at plain-speech or professional register.

Operational discipline

  • Trace every retrieval stage. OpenTelemetry spans for parse, each retriever, fusion, rerank, gate decision, assembly, generation, verification — with scores. Without this, debugging a bad answer is guesswork, and you will spend more time on bad answers than on features.
  • Every answer is reproducible. Persist the query, resolved filters, retrieved provision IDs with scores, the gate decision, the prompt hash, the model version, and the verifier result. When a user reports a wrong answer — or a panel member does — we replay it exactly.
  • Evaluation in CI. The golden set runs on every change to retrieval or prompts. A regression in NDCG@10 or faithfulness blocks the merge. This is the single highest-value piece of engineering process in the project.
  • Restore drills. A backup that has never been restored is not a backup. Once a month, restore to a scratch box and run the eval suite against it.

The four-person split that actually works

Split by layer, not by feature, so people own an interface rather than a screen. Data engineer owns stages 1–7 and the corpus gates — the hardest and most valuable seat. Retrieval engineer owns stages 0–5 of the query path, the golden set, and evaluation. Application engineer owns the API, documents, procedure, auth, billing. Client engineer owns Flutter, offline, web, and the curation console. The golden set is annotated by all four together — that shared session is also how everyone learns the domain.

§11Evidence

How we prove it works

The proposals set targets (NDCG@10 ≥ 0.75, hallucination < 2%, citation accuracy > 95%) without saying what they would be measured against. That instrument has to be built first, and it is worth building well — Pakistan has no public legal IR benchmark, so it is publishable on its own.

11.1The golden set

  • 500 queries, stratified: 40% citizen-scenario, 25% professional lookup, 15% procedural, 10% Urdu or Roman Urdu, 10% deliberately unanswerable from our corpus.
  • That last stratum is the one everyone forgets and the only way to measure abstention honestly. Without it, a system that always answers looks perfect.
  • Graded relevance per query (0–3) over provisions, annotated by two people independently, with Cohen’s κ reported. If agreement is poor the metric is noise, and better to know that in week 4.
  • Frozen test split, never used for tuning. Separate dev split for threshold calibration and reranker training.

Each of these isolates one architectural claim, and each one is a figure:

  • BM25 only → dense only → hybrid → hybrid + rerank → + graph expansion. Shows each stage earning its place.
  • Off-the-shelf reranker versus fine-tuned. This is the fine-tuning contribution, quantified.

  • Translation-pipeline CLIR versus direct cross-lingual retrieval. Tests the departure in §2 D4 rather than assuming it.
